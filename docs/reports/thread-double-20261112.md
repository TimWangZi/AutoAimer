# 双线程双缓冲实机验证

> 这是 20261112 对应版本的历史验证记录。文中原始日志、画布和二进制路径位于本地 `test-results/thread-double-20261112/`，不包含在源码仓库中。

日期：2026-11-12。平台：标准 Luckfox Pico RV1103、GC9A01 240×240、无摄像头合成输入。

**`std::thread` 在当前 SDK/uClibc 和板端运行库上可用。新版已经部署，平均实际送屏帧率 29.73 FPS，比本轮单线程基线均值 21.72 FPS 提升 36.88%。**

## 线程与缓冲区

主线程负责取帧、传感器与按键接口、菜单更新、HUD 和图像合成；新增的一个标准 C++ 线程只调用同步显示接口。`DisplayWorker` 用 `std::mutex` 和 `std::condition_variable` 管理两块画布的归属。CMake 使用 `find_package(Threads REQUIRED)` 与 `Threads::Threads`；工具链实际检测到 pthread 支持由系统库提供，不需要修改 SDK 或上传新运行库。[CMake FindThreads 文档](https://cmake.org/cmake/help/latest/module/FindThreads.html)

两块最终 RGB565 画布各 115,200 字节，共 230,400 字节，比单缓冲增加 112.5 KiB。取帧、HUD 和 RGA 仍只由主线程操作，RGA 转换缓冲没有复制两份。发送线程只借用像素地址，没有第三块完整输出画布，也没有交接时的整帧拷贝。

发送中的画布只读。主线程在拿到输入、即将合成时领取另一块画布；如果这块存有尚未发送的旧帧，就收回并写新画面。完整帧提交后才可被发送线程读取。旧帧可丢弃，不积压 FIFO 队列；当发送结束时另一块仍在合成，发送线程会等待下一张完整帧。

锁只用于索引、失败状态和归属切换，不跨越合成或 SPI 发送。退出时送完最后一张已提交完整帧并 join；发送错误回传主线程。退出信号使用经工具链验证为无锁的 `std::atomic<bool>`。`--frames N` 表示合成 N 帧，实际送屏帧数可以更少；`--ppm` 在发送线程结束后保存最后合成帧。

## 验证

- SDK 编译的标准线程探针在 Pico 上运行成功，包含 `std::thread`、互斥锁、条件变量与无锁原子检查。
- Ubuntu 完整 CTest **7/7 通过**，新增并发测试覆盖发送中缓冲区不变、待发送旧帧替换、半帧不发送、空闲退出、最终帧排空、错误回传、2000 帧并发交接。测试保留在 `tests/`，生产循环没有测试分支。
- 四个菜单预览与单线程版逐字节一致。合成器测试验证两块输出互不覆盖。
- ThreadSanitizer 最终检查返回 0、无警告。最初遇到旧 TSan 的地址映射问题和未拦截 `pthread_cond_clockwait` 导致的测试假警告；只为测试进程使用 `setarch -R`，并把测试超时等待改为 `system_clock` 的 `wait_until`。未屏蔽警告，未修改生产代码的等待实现或系统全局设置。对应问题见 [GCC sanitizer/101978](https://gcc.gnu.org/pipermail/gcc-bugs/2022-July/793323.html)，完整前后日志保留在 `thread-verification.json`。
- ARM 版并发单元测试也在 Pico 上通过。无摄像头与相机/RGA 两个 ARM 应用均编译成功，只部署无摄像头版本。
- Ubuntu 的 12 帧有限运行正常退出；Pico 上同样运行 12 帧后正常退出，最终 PPM 与 Ubuntu SHA-256 一致：`df125beaf1478cda35724bb26527418bdbfcbb8ddc938469944ef6145c101c21`。

## A/B/A 对照

按单线程 → 双线程 → 单线程运行，每轮预热 3 秒、采样约 30 秒，拆成三个约 10 秒区间。以 `spi0.0/statistics/bytes_tx` 增量除以每帧 **93,770 字节**和单调时钟时长计算送屏速率。条带裁剪、30 个窗口、180 次事务、SPI 请求频率 40 MHz 全部保持不变。

| 版本 | 测量秒数 | 三个区间 FPS | 平均 FPS | 平均 ms/帧 |
|---|---:|---|---:|---:|
| 单线程（前） | 29.999 | 21.78 / 21.64 / 21.66 | 21.694 | 46.095 |
| 双线程 | 29.997 | 29.70 / 29.77 / 29.73 | 29.732 | 33.634 |
| 单线程（后） | 29.999 | 21.83 / 21.72 / 21.70 | 21.749 | 45.979 |

前后单线程 FPS 均值为 **21.721770**，双线程为 **29.732159**，提升 **36.8772%**。按吞吐率倒数计算，每帧由 **46.0368 ms** 降至 **33.6336 ms**，减少 **12.4031 ms**。这不是逐阶段计时或端到端延迟测量。

| 版本 | 线程数 | 进程 CPU 占用 | RSS | 四个采样点 CPU MHz | SPI 错误 / 超时增量 |
|---|---:|---:|---:|---|---|
| 单线程（前） | 1 | 43.63% | 2384 KiB | 1104 / 1104 / 816 / 1104 | 0 / 0 |
| 双线程 | 2 | 97.51% | 2588 KiB | 1104 / 1104 / 1104 / 1104 | 0 / 0 |
| 单线程（后） | 1 | 43.53% | 2420 KiB | 816 / 1104 / 816 / 816 | 0 / 0 |

CPU 占用由进程累计用户态与内核态时钟计算，按一个 CPU 核心归一化。governor 始终为 `ondemand`，频率自动变化，没有手动调频；这里只记录采样点频率。所有运行均正常响应 SIGTERM，返回码为 0。

主要代价是 CPU 接近满载：主线程继续合成最新输入，其中一部分完整帧在发送前被更新帧替代。RSS 相比前后基线均值增加约 **186 KiB**。限制合成节拍可能减少这些被丢弃帧的计算，但需要另外评估画面新鲜度，本轮未实施。

结果只覆盖当前无摄像头路径的短时测试，不代表实际相机吞吐、面板扫描频率或长期温度表现。保留当前调频策略意味着收益包含线程重叠和自动调频下的整体效果，不能当成固定频率下的纯并行加速比例。
